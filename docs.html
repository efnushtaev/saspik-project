⧫ Проект САСПИК

Сеть автоматизированных систем для производства и контроля

Программно-аппаратная платформа для организации совместного производства, построенная на принципах децентрализации и модульности.

Система позволяет гибко объединять оборудование, управлять производственными процессами и обмениваться данными между участниками в реальном времени.

Промо-лендинг проекта

Иерархия системы

⧫ Кластер

Базовый автономный элемент распределённой сети САСПИК.
Может быть развёрнут как в удалённом облаке, так и на локальном сервере предприятия.
Каждый Кластер независим, но при необходимости может взаимодействовать с другими Кластерами через защищённые каналы.

⧫ Юнит

Составная часть кластера, выделяемая по функциональному назначению (например, «теплица», «цех», «склад», «логистический хаб»).
В рамках одного Кластера может быть развёрнуто произвольное количество Юнитов разного типа.
Объединение существующих и добавление новых Юнитов в Кластер и их конфигурация выполняются пользователем через UI управления платформы.

⧫ Объект

Отдельное физическое или виртуальное устройство (датчик, контроллер, станок, камера, шлюз и т.д.).
Объекты подключаются к платформе для управления, мониторинга и обмена данными между собой.
Может быть частью любого Юнита (гибкая привязка), что позволяет перенастраивать логику работы без физического переподключения.

Ключевые особенности

  • Децентрализация – отсутствие единой точки отказа, каждый Кластер работает автономно.

  • Масштабируемость – добавление новых Кластеров, Юнитов и Объектов не требует остановки системы.

  • Гибкость – пользователь сам определяет структуру и связи между элементами.

  • Безопасность – все обмены данных шифруются, разграничение доступа на уровне Юнитов и Объектов.

  • Кроссплатформенность – поддержка облачных и локальных развёртываний.

⧫ Saspik-cluster

Микросервисное ядро САСПИК на NodeJS

Центральный узел платформы САСПИК, объединяющий оборудование и процессы в единую управляемую систему.

Кластер собирает данные со всех подключённых устройств, даёт пользователю единую точку управления через веб-интерфейс и связывает элементы сети (Юниты и Объекты) в гибкую иерархию.

Его задача — быть надёжным и независимым ядром: каждый кластер работает сам по себе, но при необходимости может взаимодействовать с другими кластерами, сохраняя целостность системы при любом масштабе.

Архитектура

  • Frontend: React SPA, обслуживается через Nginx. Отображает список Юнитов, сенсоры и устройства, вложенные в каждый Юнит. Поддерживает создание/редактирование/удаление Юнитов и Объектов.
  • MongoDB: Документная БД. Хранит Юниты, Объекты и правила (коллекции units, objects, rules). При первой инициализации заполняется сидами из server/src/data/*.config.ts и server/data/rules.json.
  • InfluxDB: Time-series база данных. Хранит все MQTT-сообщения от устройств.
  • Telegraf: Подписывается на все MQTT-топики (#), парсит JSON и пишет в InfluxDB.
  • Backend: Express.js сервер. Читает Юниты/Объекты/правила из MongoDB, последние значения объектов из InfluxDB и отдаёт их через REST API.
  • Nginx: Обратный прокси: статика фронтенда, прокси /api/* на backend.
  • Mosquitto: MQTT-брокер для обмена данными с устройствами.
  • MQTT Rule Engine: Получает правила из MongoDB (или HTTP API/файла), обрабатывает MQTT-сообщения и выполняет правила климат-контроля (температура/влажность).

Функциональность

  • Список юнитов с карточками
  • Создание юнита через кнопку «＋ Добавить юнит» на главной странице: модальное окно с полями (ID, название, описание). Кнопка создания скрыта в мок-режиме из коробки только по условию — в реальном режиме создание через POST /api/v1/units
  • Страница юнита (роут /unit/:unitId/info): просмотр параметров (ID, название, описание, количество объектов), редактирование (ID — только чтение) и удаление с подтверждением. Удаление юнита каскадно удаляет его объекты (сервер). Открывается по клику на карточку юнита
  • Кнопка «＋ Добавить объект» на странице юнита — открывает модалку создания объекта. Видна всегда, в том числе для юнита без объектов (пустой юнит открывается и позволяет добавить первый объект)
  • Мониторинг сенсоров (температура, влажность, давление и т.д.)
  • Автоматика — объекты автоматизации
  • Сценарии (роуты /rules и /unit/:unitId/rules): карточки правил с названием, топиком триггера и переключателем Вкл/Выкл (PATCH /api/v1/rules/:id, тело { enabled }). Список опрашивается каждые 5 сек и обновляется по DOM-событию rules-updated. Мок-API: getRulesList, setRuleEnabled
  • Динамический заголовок верхней панели: имя юнита на его страницах через PageHeaderProvider и хук use-unit-page-header
  • Создание нового объекта через кнопку «+» на страницах с выбранным юнитом: модальное окно с полями DTO (название, ID, тип, описание, замеры spec) и автогенерацией топика по паттерну `${type}/${unitId}/${id}`. Кнопка скрыта, если юнит не выбран (?id= отсутствует)
  • Страница объекта (роут /unit/:unitId/object/:objectId): просмотр данных в виде таблиц (параметры и замеры), редактирование в табличной форме (ID — только чтение) и удаление с подтверждением. Открывается по иконке «⋯» в правом верхнем углу карточки
  • Общая форма ObjectFormFields с вариантами отображения: stacked (модалка создания) и table (страница редактирования)
  • Общая форма UnitFormFields (аналогично: stacked — модалка создания юнита, table — страница редактирования)
  • 4 таба навигации: Мониторинг, Автоматика, Сценарии, Информация
  • «Живые» часы с синхронизацией через /api/getTimestamp и локальным тиком каждую секунду
  • Адаптивная вёрстка (mobile < 800px / desktop)
  • Тёмная тема через CSS-переменные
  • Mock-режим (REACT_APP_MOCK_MODE=true) — работа без сервера

Configuration Details

Broker Settings (mosquitto.conf)

  • Listens on port 1883 (MQTT) and 9001 (WebSockets)
  • Authentication enabled (allow_anonymous false)
  • Password file: /mosquitto/config/passwordfile
  • Debug logging enabled
  • ACL file: /mosquitto/config/mosquitto.acl

Access Control (mosquitto.acl)

Current ACL provides:

  1. Default deny — все неразрешённые топики блокируются
  2. Client namespaces: clients/%c/# — каждый клиент может писать/читать в свой namespace
  3. Топики датчиков: sensor/# — publish/subscribe для сенсоров
  4. Топики LED (dev): led/# — publish/subscribe для LED-устройств
  5. Топики команд юнитов: units/# — publish/subscribe для управления реле (добавлено 2026-07-27)

Client ID Based Topic Separation

The user requested: "для clientId=1 будут доступны топики 'test1', для clientId=2 будут доступны топики 'test2'"

Implemented Solution

Due to Mosquitto ACL limitations with anonymous access, we implemented namespace-based separation:

  • Client "1" → topics: clients/1/test1, clients/1/#
  • Client "2" → topics: clients/2/test2, clients/2/#

Alternative Approaches

  1. With authentication: Use client directive in ACL for exact topic names
  2. Application-level validation: Validate clientId in LocalMqttService
  3. Topic rewriting: Server rewrites test1 → clients/1/test1

Troubleshooting

Broker not starting

Check ACL syntax:

docker run --rm -it eclipse-mosquitto:2.0 mosquitto -c /mosquitto/config/mosquitto.conf --test

Connection refused

  • Ensure port 1883 is not blocked
  • Check if another Mosquitto instance is running
  • Verify Docker container is up: docker ps | grep mosquitto

ACL not enforcing

  • Mosquitto requires authentication for client directives
  • With allow_anonymous true, only pattern directives work
  • Check broker logs for ACL parse errors

⧫ MQTT Rule Engine Worker

Движок правил для MQTT: автоматическое выполнение действий по условиям

Правила загружаются из MongoDB, HTTP API или файла и обновляются в рантайме без остановки процесса.

Основные компоненты:

  • Ядро (RuleEngine) — управление подписками, оценка условий, выполнение действий
  • MQTT (MqttAdapter) — абстракция над библиотекой mqtt; подключение к брокеру, публикация и подписка
  • Условия (Condition) — проверка топика по regex, JSONPath, точное совпадение payload, логические композиты (AND, OR, NOT), диапазон времени (timeBetween)
  • Действия (Action) — публикация в топик, логирование в консоль, отложенное выполнение (timeout)
  • Провайдеры правил (RulesProvider) — MongoRulesProvider, ApiRulesProvider, фабрика createRulesProvider
  • Конфигурация — RuleBuilder (парсинг JSON-правил), ConfigWatcher (файловый источник с fs.watch)
  • Контекст (MessageContext) — доступ к payload как JSON, извлечение значений по JSONPath

Технические детали:

  • TypeScript, Node.js 18+
  • MQTT (библиотека mqtt), MongoDB (официальный драйвер)
  • tslog, ts-node (разработка)

Формат правила

Правило в MongoDB/API хранится в формате rule-engine. Поле enabled: false — «мягкое» отключение: движок пропускает такое правило и не подписывается на его топики.

{
  "id": "temp_emergency_high",
  "trigger": { "topic": "sensor/${CLIMATE_CONTROL_UNIT_ID}/dht22", "qos": 0 },
  "when": { "jsonpath": "$.temperature > 29" },
  "then": [
    { "action": "publish", "params": { "topic": "units/unitId1/commands/a_relay3", "payload": "{\"state\":\"1\"}", "qos": 1 } }
  ],
  "enabled": true
}

Триггер (trigger)

  • topic — строка или массив строк. Поддерживает MQTT wildcards + (один уровень) и # (много уровней)
  • qos — уровень качества обслуживания (0, 1, 2). По умолчанию 0

Условия (when)

Условие может быть опущено — тогда правило срабатывает на любое сообщение в топике.

Тип Параметр Пример
topicRegex Регулярное выражение для топика "^sensor/.+/status$"
jsonpath Выражение $.field оператор значение "$.temperature > 30"
payloadEquals Точное совпадение payload как строки "OK"
timeBetween Диапазон времени срабатывания { "from": "22:00", "to": "06:00" }
and Массив условий (логическое И) [{"topicRegex": "^sensor/.+"}, {"jsonpath": "$.value > 0"}]
or Массив условий (логическое ИЛИ) аналогично and
not Одно условие (логическое НЕ) {"topicRegex": "^test/.+"}

Действия (then)

Массив действий, выполняемых последовательно при срабатывании правила.

publish — публикация в топик

При записи в БД подставляются переменные окружения (${ENV_VAR}) и выражения (${expr:...}).

{
  "rules": [
    {
      "id": "unique_rule_id",
      "name": "Температурный порог",
      "unitId": "unit-id-1",
      "trigger": {
        "topic": "sensor/unit-id-1/dht22",
        "qos": 0
      },
      "when": {
        "jsonpath": "$.temperature > 30"
      },
      "then": [
        {
          "action": "log",
          "params": {
            "level": "warn",
            "message": "Температура превысила порог: {{temperature}}°C"
          }
        },
        {
          "action": "publish",
          "params": {
            "topic": "alerts/high_temperature",
            "payload": "{\"value\": {{temperature}}, \"timestamp\": \"{{timestamp}}\"}",
            "qos": 1,
            "retain": false
          }
        }
      ],
      "enabled": true
    }
  ]
}

Структура

Поле Описание
id Уникальный идентификатор правила
name Название правила (опционально)
unitId ID юнита, к которому относится правило
trigger.topic Топик MQTT (строка или массив, поддерживает + и #)
trigger.qos Уровень QoS (0, 1, 2), по умолчанию 0
when Условие срабатывания (может быть опущено)
then Массив действий (не пустой)
enabled Флаг включения: правила с enabled: false не загружаются движком

Типы условий (when)

Тип Параметр Пример
topicRegex RegExp для топика "^sensor/.+/status$"
jsonpath $.field оператор значение "$.temperature > 30"
payloadEquals Точное совпадение payload "OK"
and Массив условий (И) [{...}, {...}]
or Массив условий (ИЛИ) [{...}, {...}]
not Одно условие (НЕ) {...}
timeBetween Временной интервал по часу (см. ниже) { "start": 22, "end": 6 }

Операторы jsonpath: ==, !=, >, >=, <, <=.
timeBetween — срабатывает, если текущий час (с учётом MOSCOW_OFFSET_HOUR, по умолчанию 3) попадает в интервал [start, end). При start > end интервал считается «через полночь». Параметры: start (number), end (number), опционально field — путь к ISO-дате в payload (иначе используется время получения сообщения).

{ "when": { "timeBetween": { "start": 22, "end": 6 } } }

Типы действий (then)

log — логирование в консоль:

  • level: info, warn, error
  • message: строка с плейсхолдерами {{fieldName}}

publish — публикация в топик:

  • topic: топик назначения
  • payload: строка с плейсхолдерами {{fieldName}}
  • qos: QoS (0, 1, 2), по умолчанию 0
  • retain: флаг retain (true/false), по умолчанию false

timeout — отложенный запуск вложенных действий:

  • delay: задержка в миллисекундах
  • then: массив действий, выполняемых после задержки
{ "action": "timeout", "params": { "delay": 5000, "then": [ { "action": "publish", "params": { "topic": "alerts/slow", "payload": "1" } } ] } }

Плейсхолдеры {{fieldName}} в payload/message заменяются значениями из JSON-контекста сообщения (доступ через jsonpath-путь $.fieldName).

Источники правил

Движок получает правила через провайдер, источник задаётся переменной RULES_SOURCE:

Источник Провайдер Поведение
mongo (по умолчанию) MongoRulesProvider Поллинг коллекции rules каждые 5 с (RULES_POLL_INTERVAL_MS), фильтр enabled !== false
api ApiRulesProvider Поллинг GET RULES_API_URL каждые 5 с, ожидает { "rules": [...] }, фильтр enabled !== false
file ConfigWatcher Следит за файлом CONFIG_PATH (по умолчанию ./rules.json), перечитывает при изменении

Во всех режимах набор правил пересобирается только при изменении сигнатуры (полного JSON) — при неизменных данных провайдер не вызывает перезагрузку. Изменение enabled в БД/API автоматически применяется движком на следующем поллинге (правило исключается из обработки).

MQTT_BROKER_URL=mqtt://localhost:1883 CONFIG_PATH=./rules.json npm start

Для MongoDB-режима: RULES_SOURCE=mongo MONGODB_URL=mongodb://... npm start.

Камера выращивания — гидропонная установка на 2 куста

1. Описание

Гидропонная установка для клубники на основе канализационной трубы ПВХ ø200 мм. Метод — частичное затопление (ebb & flow). Питательный раствор подаётся сверху помпой, заполняет трубу до уровня перелива, затем самотеком сливается обратно в бак. Управление помпой через ESP32 + MQTT + rule-engine (SASPIK Cluster).

Параметры:

  • Количество кустов: 2
  • Субстрат: перлит
  • Длина трубы: 500–600 мм
  • Уровень заполнения: ~50 мм
  • Расположение бака: снизу под трубой, горизонтально, из той же трубы ø200 мм
  • Объём бака: ~15.7 л (500 мм длины)

2. Схема

Сенсорная камера — герметичный пластиковый корпус (ø75 мм × 100 мм) с вертикальным стояком-переливом внутри. При каждом сливе раствора из основной трубы камера заполняется, старая порция вытесняется через стояк в бак. После завершения слива в камере остаётся ~40 мм раствора, закрывающего датчики. При следующем цикле затопления новая порция промывает камеру и заменяет раствор.

4. Сборка

  1. Торцы: приклеить заглушки к обоим торцам трубы клеем для ПВХ.

  2. Слив: в дне трубы (в нижней точке уклона) вырезать отверстие под муфту ø50 мм. Вклеить муфту с переходом на шланг слива в бак.

  3. Отверстия под стаканы: разметить по центру верхней части трубы с шагом ~250 мм. Вырезать отверстия ø50–60 мм (по размеру стаканов).

  4. Перелив: в торцевой заглушке (противоположной сливу) или в верхней стенке установить вертикальный стояк высотой ~50 мм от дна трубы. Через него будет уходить избыток раствора.

  5. Подача: закрепить штуцер для трубки 8 мм сверху трубы. Трубка от помпы идёт вверх, вводится в трубу через штуцер.

  6. Уклон: установить трубу с уклоном ~2° в сторону слива (≈ 10 мм перепад на 500 мм длины).

  7. Помпа: поместить помпу в бак, подключить трубку подачи. Бак поставить под сливным отверстием.

  8. Стаканы: заполнить стаканы перлитом, установить в отверстия. Стаканы должны входить плотно, но до дна трубы не доставать (≈ 10–20 мм зазора).

  9. Бак:

    • Взять отрезок трубы ø200 мм × 500 мм.
    • Приклеить заглушки к обоим торцам.
    • Врезать штуцер 8 мм в нижней части одной из стенок — для забора раствора помпой.
    • В верхней части противоположной стенки врезать штуцер/фитинг для слива из сенсорной камеры.
    • В верхней части сделать отверстие под воздушный клапан (или просто небольшое отверстие ø3 мм для выравнивания давления).
    • Установить бак горизонтально под сливом из сенсорной камеры. Помпу разместить внутри бака или снаружи на заборном штуцере.

  10. Сенсорная камера:

  • Приклеить заглушку к нижнему торцу трубы ø75 мм (дно камеры).
  • Установить вертикальный стояк ø8 мм в дне камеры (высота 40 мм). Стояк — трубка, выходящая через дно наружу и отводящая избыток раствора в бак. Герметизировать место прохода.
  • Врезать входной фитинг в верхней части стенки камеры (от слива из основной трубы).
  • Закрепить датчики pH и EC через герметичные вводы в боковой стенке или сверху. Чувствительные элементы должны располагаться на высоте ~20 мм от дна (чтобы всегда были в растворе после слива).
  • Соединить слив из основной трубы с входом сенсорной камеры трубкой ø8 мм. Выход стояка направить в бак.

5. Подключение к SASPIK

  • ESP32 управляет реле помпы по MQTT-командам
  • MQTT-топик: greenhouse/grow_chamber/command
  • Формат команды: {"state":"ON"} / {"state":"OFF"}
  • Цикл затопления настраивается через rule-engine в saspik-cluster (например: помпа ON на 10 мин, OFF на 50 мин)
  • Датчик уровня в трубе или таймер определяет длительность цикла

Утверждённая архитектура (конспект)

Каждый бот (ESP32-S3)

  • Собирает UWB-дальности до соседей, опрашивает IMU и энкодеры.
  • Ведёт счисление пути и вычисляет свои координаты (EKF) относительно опорных точек роя.
  • Имеет камеру OV2640 и выполняет на борту инференс простой TFLite-модели (2 класса: культура/сорняк).
  • Каждое обнаружение упаковывает в короткий пакет (свои координаты, координаты цели, класс, уверенность) и отправляет в общий LoRa-mesh.
  • Получает от базы или соседей задания на коррекцию маршрута, но может работать автономно при обрыве связи.
  • Реагирует на соседей: избегает столкновений, перераспределяет сектора покрытия по алгоритму виртуальных сил.

Базовая станция (Raspberry Pi + LoRa-модуль)

  • Участвует в mesh как привилегированный узел.
  • Аккумулирует все пакеты с детекциями.
  • Строит единую оперативную карту прополки/посева.
  • Выявляет пропущенные участки, оптимизирует глобальное покрытие.
  • Отправляет ботам рекомендательные команды («проверить зону», «сместить фокус»).
  • Предоставляет веб-интерфейс оператору с картой, статусом, зарядом.

Локальная версия для первых тестов (Docker)

На этапах 1–3 базовая станция запускается локально в Docker на машине разработчика:

  • Принимает UART-логи с ESP32 через проброшенный USB (последовательный порт).
  • Логирует и отображает дальномерные данные, позже — координаты и LoRa-пакеты.
  • Веб-интерфейс (FastAPI + легковесный фронтенд) для визуализации в реальном времени.
  • Контейнерная сборка: одна команда docker compose up для поднятия всего стека.
  • Переход на RPi произойдёт на этапе полевых испытаний (Stage 4–5).

Сеть

  • UWB — для точной относительной навигации (без GPS).
  • LoRa (433/868 МГц, mesh) — для обмена координатами, статусом, метаданными детекций и командами.
  • Данные, передаваемые по LoRa, компактны (50–150 байт), что укладывается в возможности технологии.
  • Никакой сырой видеопоток по LoRa не идёт.

Дополнительно (опция, не для MVP)

Позже можно добавить Raspberry Pi на отдельных ботов-лидеров, если понадобится более сложное зрение прямо в поле. Но текущий стек позволяет начать без него.

Что у вас есть сейчас для немедленного старта

  • Чёткая архитектура с разделением обязанностей.
  • Понимание, что и на чём работает: ESP32-S3 для real-time + простого зрения, RPi для оркестрации.
  • Определённый стек протоколов: UWB (TWR), LoRa-mesh (flooding или gossip), бинарные пакеты.
  • План первого шага: оживить UWB-дальномер на двух ESP32.

Соединение ESP32-S3 ↔ DWM3000 (SPI)

ESP32-S3           DWM3000 (24-pin QFN модуль)
────────           ───────────────────────────
GPIO 10 (SPI CS)   →  CS
GPIO 11 (SPI MOSI) →  MOSI
GPIO 12 (SPI MISO) ←  MISO
GPIO 13 (SPI SCK)  →  SCK
GPIO 14            →  RSTn
GPIO 15            ←  IRQ
3.3V               →  VCC / VCC2
GND                →  GND

Пин-аут требует сверки с даташитом DWM3000 (Qorvo). В отличие от DWM1000, у DWM3000 часть пинов переключена. Перед разводкой платы обязательно сверить назначение по документации.

Питание

LiPo 3.7V → LDO 3.3V → ESP32-S3 VDD33
                     → DWM3000 VCC + VCC2 (3.3V, оба пина)

DWM3000 VDD — выход внутреннего регулятора 1.8В (C8 между VDD и GND)

Стенд для Stage 1 (два узла)

[USB]──[ESP32 #1]──[UWB] ~~~~~~~~ [UWB]──[ESP32 #2]──[USB]
         │                                            │
      UART(лог)                                   UART(лог)
  • Оба узла идентичны по схеме.
  • Питание через USB от ноутбука.
  • Связь UWB — двусторонняя дальнометрия (TWR).

Альтернативные пины для кастомной платы

Если SPI-порты заняты, можно использовать HSPI (GPIO 26–29) вместо SPI2:

HSPI: CS=26, MOSI=27, MISO=28, SCK=29

Известные проблемы схемы

  • Пин-аут DWM3000 требует верификации — в текущей схеме используются предположительные соединения по аналогии с DWM1000.
