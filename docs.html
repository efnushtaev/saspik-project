⧫ Проект САСПИК

Сеть автоматизированных систем для производства и контроля

Программно-аппаратная платформа для организации совместного производства, построенная на принципах децентрализации и модульности.

Система позволяет гибко объединять оборудование, управлять производственными процессами и обмениваться данными между участниками в реальном времени.

Промо-лендинг проекта

Иерархия системы

Кластер

Базовый автономный элемент распределённой сети САСПИК.
Может быть развёрнут как в удалённом облаке, так и на локальном сервере предприятия.
Каждый Кластер независим, но при необходимости может взаимодействовать с другими Кластерами через защищённые каналы.

Юнит

Составная часть кластера, выделяемая по функциональному назначению (например, «теплица», «цех», «склад», «логистический хаб»).
В рамках одного Кластера может быть развёрнуто произвольное количество Юнитов разного типа.
Объединение существующих и добавление новых Юнитов в Кластер и их конфигурация выполняются пользователем через UI управления платформы.

Объект

Отдельное физическое или виртуальное устройство (датчик, контроллер, станок, камера, шлюз и т.д.).
Объекты подключаются к платформе для управления, мониторинга и обмена данными между собой.
Может быть частью любого Юнита (гибкая привязка), что позволяет перенастраивать логику работы без физического переподключения.

Ключевые особенности

  • Децентрализация – отсутствие единой точки отказа, каждый Кластер работает автономно.

  • Масштабируемость – добавление новых Кластеров, Юнитов и Объектов не требует остановки системы.

  • Гибкость – пользователь сам определяет структуру и связи между элементами.

  • Безопасность – все обмены данных шифруются, разграничение доступа на уровне Юнитов и Объектов.

  • Кроссплатформенность – поддержка облачных и локальных развёртываний.

⧫ Saspik-cluster

Микросервисное ядро САСПИК на NodeJS

Центральный узел платформы САСПИК, объединяющий оборудование и процессы в единую управляемую систему.

Кластер собирает данные со всех подключённых устройств, даёт пользователю единую точку управления через веб-интерфейс и связывает элементы сети (Юниты и Объекты) в гибкую иерархию.

Его задача — быть надёжным и независимым ядром: каждый кластер работает сам по себе, но при необходимости может взаимодействовать с другими кластерами, сохраняя целостность системы при любом масштабе.

Функциональные компоненты

Компонент Описание
server API. ExpressJS бэкенд (микросервисная архитектура на Inversify)
client UI, React SPA (CRA + TypeScript), панель управления IoT-кластером

Архитектура

  • Frontend: React SPA, обслуживается через Nginx. Отображает список Юнитов, сенсоры и устройства, вложенные в каждый Юнит. Поддерживает создание/редактирование/удаление Юнитов и Объектов.
  • MongoDB: Документная БД. Хранит Юниты, Объекты и правила (коллекции units, objects, rules). При первой инициализации заполняется сидами из server/src/data/*.config.ts и server/data/rules.json.
  • InfluxDB: Time-series база данных. Бакет mqtt — сенсорные/командные данные; бакет logs (retention 7 дней) — логи-конверты device/server/rule-engine.
  • Telegraf: Подписывается на MQTT-топики (данные → measurement mqtt_consumer, логи → measurement logs), парсит JSON и пишет в соответствующие бакеты InfluxDB.
  • Backend: Express.js сервер. Читает Юниты/Объекты/правила из MongoDB, последние значения объектов из InfluxDB и отдаёт их через REST API.
  • Nginx: Обратный прокси: статика фронтенда, прокси /api/* на backend.
  • Mosquitto: MQTT-брокер для обмена данными с устройствами.
  • MQTT Rule Engine: Получает правила из MongoDB (или HTTP API/файла), обрабатывает MQTT-сообщения и выполняет правила климат-контроля (температура/влажность).

⧫ Saspik-cluster — Фронтенд

React SPA для панели управления IoT-кластером

Реализована на CRA + TypeScript, React 19, react-router-dom 6, иконки @ant-design/icons, BEM-стилизация (bem-react-classname)

Поддерживает мок-режим без бэкенда

Функциональность

  • Список юнитов с карточками
  • Создание юнита через кнопку «＋ Добавить юнит» в панели действий (action-field) на главной странице: модальное окно с полями (ID, название, описание). Кнопка создания скрыта в мок-режиме из коробки только по условию — в реальном режиме создание через POST /api/v1/units
  • Страница юнита (роут /unit/:unitId/info): просмотр параметров (ID, название, описание, количество объектов), редактирование (ID — только чтение) и удаление с подтверждением. Удаление юнита каскадно удаляет его объекты (сервер). Открывается по клику на карточку юнита
  • Кнопка «＋ Добавить объект» в панели действий (action-field) на страницах «Мониторинг» и «Автоматика» юнита — открывает модалку создания объекта. Видна и для юнита без объектов (пустой юнит открывается и позволяет добавить первый объект)
  • Мониторинг сенсоров (температура, влажность, давление и т.д.)
  • Автоматика — объекты автоматизации
  • Сценарии (роуты /rules и /unit/:unitId/rules): карточки правил с названием, топиком триггера и переключателем Вкл/Выкл (PATCH /api/v1/rules/:id, тело { enabled }). Список опрашивается каждые 5 сек и обновляется по DOM-событию rules-updated. Мок-API: getRulesList, setRuleEnabled
  • Хлебные крошки в верхней панели на страницах юнита: «Все юниты → <Имя юнита>»; ссылка «Все юниты» ведёт на главную. Имя юнита и заголовки страниц задаются через PageHeaderProvider, хуки use-unit-name и use-unit-page-header
  • Создание нового объекта через кнопку «＋ Добавить объект» на страницах «Мониторинг» и «Автоматика» юнита: модальное окно с полями DTO (название, ID, тип, описание, замеры spec) и автогенерацией топика по паттерну `${type}/${unitId}/${id}`. Кнопка скрыта на главной и на странице объекта
  • Страница объекта (роут /unit/:unitId/object/:objectId): просмотр данных в виде таблиц (параметры и замеры), редактирование в табличной форме (ID — только чтение) и удаление с подтверждением. Открывается по иконке «⋯» в правом верхнем углу карточки
  • Общая форма ObjectFormFields с вариантами отображения: stacked (модалка создания) и table (страница редактирования)
  • Общая форма UnitFormFields (аналогично: stacked — модалка создания юнита, table — страница редактирования)
  • 4 таба навигации: Мониторинг, Автоматика, Сценарии, Информация
  • «Живые» часы с синхронизацией через /api/getTimestamp и локальным тиком каждую секунду
  • Адаптивная вёрстка (mobile < 800px / desktop)
  • Тёмная тема через CSS-переменные
  • Mock-режим (REACT_APP_MOCK_MODE=true) — работа без сервера

npm start              # dev-режим, бэкенд на :3001
npm run start:mock     # мок-режим, бэкенд не нужен
npm run build          # production-сборка

⧫ InfluxDB — бакеты и retention

Time-series база данных (InfluxDB 2.x) для сенсорных данных и логов

InfluxDB 2.x хранит данные от Telegraf.
Образ собирается локально из influxdb/Dockerfile (FROM influxdb:2.9.1).
В образ вшит каталог provision/ — никаких bind-mount'ов скриптов в compose, они всегда доступны
внутри образа по пути /provision/ (важно для деплоя через Portainer из Git,
где bind-mount на недостающий каталог на сервере падал бы).

Бакеты

Бакет ENV (default) Retention Содержимое
Основной INFLUXDB_BUCKET (напр. mqtt) задаётся DOCKER_INFLUXDB_INIT_* сенсорные/командные данные (measurement mqtt_consumer)
Логи INFLUXDB_LOGS_BUCKET (logs) INFLUXDB_LOGS_RETENTION_DAYS (7) логи-конверты device/server/rule-engine (measurement logs)

Инициализация

Основной бакет/пользователь создаются через env контейнера DOCKER_INFLUXDB_INIT_* при первом старте.

Бакет logs с retention 7 дней создаётся вместе с основным бакетом на каждом
старте контейнера обёрткой provision/bootstrap.sh (лежит в образе):

  • bootstrap.sh — entrypoint-обёртка: запускает штатный /entrypoint.sh influxd
    (на свежем volume он выполняет setup и создаёт org/токен/бакет mqtt),
    дожидается API на :8086 (до 300 с) и вызывает ensure-buckets.sh.
  • ensure-buckets.sh — идемпотентно создаёт бакеты из INFLUXDB_BUCKETS
    (по умолчанию mqtt,logs), если их нет. logs — с retention
    INFLUXDB_LOGS_RETENTION_DAYS (по умолчанию 7 дней), mqtt — без retention.
    Токен/org берёт из INFLUXDB_TOKEN/INFLUXDB_ORG, при их отсутствии —
    из DOCKER_INFLUXDB_INIT_ADMIN_TOKEN/DOCKER_INFLUXDB_INIT_ORG.

Provisioning нефатален: даже если бакеты не создались, influxd продолжает
работать на :8086 (в логах предупреждение) — provisioning не может уронить
доступность InfluxDB.

Благодаря этому бакеты гарантированно существуют и на уже инициализированном
volume (штатный /docker-entrypoint-initdb.d там не выполнялся бы).
Setup через env DOCKER_INFLUXDB_INIT_* остаётся для свежего volume — он же
создаёт служебные бакеты _monitoring и _tasks.

Переменные окружения контейнера

DOCKER_INFLUXDB_INIT_MODE=setup
DOCKER_INFLUXDB_INIT_USERNAME=admin
DOCKER_INFLUXDB_INIT_PASSWORD=admin123
DOCKER_INFLUXDB_INIT_ORG=${INFLUXDB_ORG}
DOCKER_INFLUXDB_INIT_BUCKET=${INFLUXDB_BUCKET}
DOCKER_INFLUXDB_INIT_ADMIN_TOKEN=${INFLUXDB_TOKEN}
INFLUXDB_BUCKETS=${INFLUXDB_BUCKETS:-mqtt,logs}
INFLUXDB_LOGS_RETENTION_DAYS=${INFLUXDB_LOGS_RETENTION_DAYS:-7}

⧫ Mosquitto — MQTT-брокер

Eclipse Mosquitto 2.0: шина сообщений между устройствами, backend и WebSocket-клиентами

Mosquitto — MQTT-брокер кластера.
Собирается из mqtt/Dockerfile (образ Mosquitto 2.0 с собственным конфигом).
Порты: 1883 (MQTT) и 9001 (WebSocket).
Аутентификация включена (allow_anonymous false), разграничение топиков — через ACL.

Конфигурация (mosquitto.conf)

  • Прослушивает порты 1883 (MQTT) и 9001 (WebSocket).
  • Аутентификация включена (allow_anonymous false).
  • Файл паролей: /mosquitto/config/passwordfile.
  • log_type notice (без поштучного debug — анти-спам).
  • Файл ACL: /mosquitto/config/mosquitto.acl.

Аутентификация

Учётные данные по умолчанию:

Параметр Значение
Username admin
Password password123

Файл паролей генерируется mosquitto_passwd и вшит в Docker-образ. Добавление пользователя или смена пароля:

docker exec -it saspik_mosquitto /bin/sh
mosquitto_passwd -b /mosquitto/config/passwordfile username password   # новый пользователь
mosquitto_passwd -b /mosquitto/config/passwordfile admin newpassword   # смена пароля

Правила ACL (mosquitto.acl)

Порядок правил:

  1. Default deny — все неразрешённые топики блокируются.
  2. healthcheck/# — healthcheck брокера.
  3. clients/%c/# — каждый клиент может читать/писать в свой namespace (по Client ID).
  4. sensor/# — publish/subscribe для сенсорных топиков.
  5. led/# — управление LED.
  6. units/# — publish/subscribe для топиков команд (управление реле, добавлено 2026-07-27).
  7. device/# — команды device/{unitId}/{objectId}/command, retained-состояние /state, /status и лог /log (с 2026-10-29 вместо device/+/+/log).
  8. Лог-топики backend: server/+/log, rule-engine/+/log (единый JSON-конверт, 2026-09-03).

Сводная таблица паттернов — в docs/mqtt-topics.

После изменения ACL нужна пересборка образа. mosquitto.acl и mosquitto.conf копируются в образ в mqtt/Dockerfile; docker compose restart / up -d без --build поднимают старый ACL. Используйте docker compose build mosquitto && docker compose up -d mosquitto (или bind-mount ACL).

Разделение топиков по Client ID

Namespace-подход (из-за ограничений ACL при анонимном доступе):

  • Client 1 → топики clients/1/test1, clients/1/#.
  • Client 2 → топики clients/2/test2, clients/2/#.

Альтернативы:

  1. С аутентификацией — директива client в ACL для точных имён топиков.
  2. Проверка на уровне приложения — валидация clientId в LocalMqttService.
  3. Перезапись топиков — сервер переписывает test1 → clients/1/test1.

Тестирование

node client.js                # тестовый клиент (с аутентификацией admin/password123)
node test_auth.js             # проверка аутентификации
node test_auth_clientid2.js   # аутентификация с конкретным Client ID
node test-clientid.js         # проверка ограничений по Client ID

Запуск в Docker

Брокер включён в docker-compose.yml как сервис mosquitto:

docker compose build mosquitto
docker compose up -d mosquitto
docker compose logs -f mosquitto

Диагностика

Брокер не стартует — проверить синтаксис ACL:

docker run --rm -it eclipse-mosquitto:2.0 mosquitto -c /mosquitto/config/mosquitto.conf --test

Connection refused:

  • Порт 1883 не заблокирован.
  • Не запущен другой экземпляр Mosquitto.
  • Контейнер поднят: docker ps | grep mosquitto.

ACL не применяется:

  • Для директив client Mosquitto требует аутентификацию.
  • При allow_anonymous true работают только pattern-директивы.
  • В логах брокера может быть ошибка парсинга ACL.

⧫ MQTT Rule Engine — Воркер

Движок правил для MQTT: автоматическое выполнение действий по условиям

Правила загружаются из MongoDB, HTTP API или файла и обновляются в рантайме без остановки процесса.

Основные компоненты:

  • Ядро (RuleEngine) — управление подписками, оценка условий, выполнение действий
  • MQTT (MqttAdapter) — абстракция над библиотекой mqtt; подключение к брокеру, публикация и подписка
  • Условия (Condition) — проверка топика по regex, JSONPath, точное совпадение payload, логические композиты (AND, OR, NOT), диапазон времени (timeBetween)
  • Действия (Action) — публикация в топик, логирование в консоль, отложенное выполнение (timeout)
  • Провайдеры правил (RulesProvider) — MongoRulesProvider, ApiRulesProvider, фабрика createRulesProvider
  • Конфигурация — RuleBuilder (парсинг JSON-правил), ConfigWatcher (файловый источник с fs.watch)
  • Контекст (MessageContext) — доступ к payload как JSON, извлечение значений по JSONPath

Технические детали:

  • TypeScript, Node.js 18+
  • MQTT (библиотека mqtt), MongoDB (официальный драйвер)

Формат правила

Правило в MongoDB/API хранится в формате rule-engine. Поле enabled: false — «мягкое» отключение: движок пропускает такое правило и не подписывается на его топики.

{
  "id": "temp_emergency_high",
  "trigger": { "topic": "sensor/${CLIMATE_CONTROL_UNIT_ID}/dht22", "qos": 0 },
  "when": { "jsonpath": "$.temperature > 29" },
  "then": [
    { "action": "publish", "params": { "topic": "units/unitId1/commands/a_relay3", "payload": "{\"state\":\"1\"}", "qos": 1 } }
  ],
  "enabled": true
}

Триггер (trigger)

  • topic — строка или массив строк. Поддерживает MQTT wildcards + (один уровень) и # (много уровней)
  • qos — уровень качества обслуживания (0, 1, 2). По умолчанию 0

Условия (when)

Условие может быть опущено — тогда правило срабатывает на любое сообщение в топике.

Тип Параметр Пример
topicRegex Регулярное выражение для топика "^sensor/.+/status$"
jsonpath Выражение $.field оператор значение "$.temperature > 30"
payloadEquals Точное совпадение payload как строки "OK"
timeBetween Диапазон времени срабатывания { "from": "22:00", "to": "06:00" }
and Массив условий (логическое И) [{"topicRegex": "^sensor/.+"}, {"jsonpath": "$.value > 0"}]
or Массив условий (логическое ИЛИ) аналогично and
not Одно условие (логическое НЕ) {"topicRegex": "^test/.+"}

Действия (then)

Массив действий, выполняемых последовательно при срабатывании правила.

publish — публикация в топик
Параметр Описание По умолчанию
topic Топик для публикации —
payload Строка payload, поддерживает плейсхолдеры {{field}} —
qos QoS публикации 0
retain Флаг retain false
log — логирование (консоль + лог-топик MQTT)

Выводит в консоль и публикует в топик rule-engine/worker/log единый JSON-конверт лога:
{ "level", "src": "rule-engine", "event", "msg", "topic" }. Telegraf отводит его в measurement logs в InfluxDB.

Параметр Описание По умолчанию
level Уровень: info, warn, error info
message Строка с плейсхолдерами {{field}} —

Срабатывание правила логируется движком как event=rule-fired, ошибка выполнения — event=rule-error. Входящие сообщения поштучно не логируются (анти-спам).

timeout — отложенное выполнение
Параметр Описание
delayMs Задержка в миллисекундах
then Массив действий для выполнения после задержки

Обновление правил в рантайме

Воркер опрашивает источник правил каждые RULES_POLL_INTERVAL_MS (по умолчанию 5000 мс) и пересобирает правила при изменении:

  • mongo / api — опрос по таймеру; при изменении набора правил движок обновляет подписки без остановки процесса

Правила с enabled: false пропускаются, их топики отписываются.

⧫ Telegraf — запись MQTT → InfluxDB

Подписка на MQTT-топики кластера и запись данных и логов в InfluxDB 2.x

Telegraf подписывается на топики mosquitto и пишет в InfluxDB 2.x.
Два входа mqtt_consumer и два выхода outputs.influxdb_v2 (разделение по namepass).
Measurement для данных — mqtt_consumer, для логов — logs.

Конфигурация (telegraf.conf)

Два входа mqtt_consumer и два выхода outputs.influxdb_v2 (разделение по namepass):

Вход Топики Measurement Бакет (выход)
Данные (data_format=json) sensor/#, units/# mqtt_consumer ${INFLUXDB_BUCKET} (напр. mqtt)
Логи (data_format=json) device/+/+/log, server/+/log, rule-engine/+/log logs (name_override) ${INFLUXDB_LOGS_BUCKET} (напр. logs)

Вход «Данные» намеренно не подписан на healthcheck/#: healthcheck mosquitto
публикует в healthcheck/ping payload каждые 30 с, и не-JSON payload ломал парсер
data_format=json, из-за чего падал весь батч mqtt_consumer и новые данные
не доходили до InfluxDB.

Выходы разделяют потоки через namepass:

  • namepass = ["mqtt_consumer"] → только сенсорные/командные данные в основной бакет;
  • namepass = ["logs"] → только логи в отдельный бакет logs.

Логи (measurement logs)

Теги: topic, level, event, src, unitId, objectId.
Поля: msg, cause, uptime и др. (json_string_fields = ["msg","cause"]).

Бакет logs создаётся на каждом старте InfluxDB скриптом influxdb/provision/ensure-buckets.sh
с retention INFLUXDB_LOGS_RETENTION_DAYS (по умолчанию 7 дней) — см. influxdb/README.md.
Скрипт вшит в образ InfluxDB (см. influxdb/Dockerfile).

Просмотр логов в Data Explorer

Ошибка unsupported input type for mean aggregate: string при выборе бакета logs
в Data Explorer InfluxDB (:8086) — не баг пайплайна: дефолтный запрос UI
применяет aggregateWindow(every: ..., fn: mean), а mean() во Flux работает только
с числами. Поля логов (msg, cause) — строки (json_string_fields), поэтому
агрегировать их средним нельзя. Бакет mqtt не падает, потому что там дефолтное
поле числовое (value).

Смотреть логи без ошибки можно двумя способами:

  • Сменить агрегацию в Query Builder: вместо mean выбрать last или count
    (подходят и для строковых полей).
  • Вставить готовый скрипт в Script Editor — см. influxdb/queries/logs-view.flux
    (сырые логи limit(n: 200) или last по src/topic). Вид — Table / Logs.

Ошибки в коде нет — её генерирует только Data Explorer; сервис чтения состояния
(influxDbStateStore.service.ts) использует last(), а не mean().

Переменные окружения

  • INFLUXDB_TOKEN, INFLUXDB_ORG, INFLUXDB_BUCKET — основной бакет
  • INFLUXDB_LOGS_BUCKET (default logs), INFLUXDB_LOGS_RETENTION_DAYS (default 7) — бакет логов

⧫ HTTP API

HTTP API для управления Юнитами, Объектами, правилами и командами устройствам

Базовый URL: http://<cluster-host>:<port>/api/v1.

Все маршруты монтируются с префиксом /api/v1 (API_V1_URL_PREFIX); домены — /units, /objects, /rules. Роутер /mqtt (MqttController) в приложение не смонтирован.

Служебные эндпоинты

  • GET /health (http://<cluster-host>:<port>/health, без префикса) — 200 OK, текстовый ответ OK; используется healthcheck'ом контейнера.
  • GET /api/getTimestamp (без префикса /api/v1) — { "timestamp": "2026-11-06T09:00:00.000Z" }.

Ошибки

  • Успех — 2xx с телом ответа; ошибки — JSON { "error": "<сообщение>" } с HTTP-кодом (400 — невалидный запрос, 404 — не найдено, 500 — внутренняя ошибка).
  • Исключение для команды: ошибка отдаётся как { "success": false, "error": "<сообщение>" } с кодом 500.
  • Централизованной валидации DTO нет: проверки выполняются в сервисах/контроллерах, поэтому часть некорректных запросов вернёт 400 с текстом ошибки, а не структурированный список полей.

Что происходит:

Условие Публикация
Топик объекта начинается с device/, key указан и есть в spec объекта ${topic}/command, payload {"channel":"<key>","value":"<value>"}
key не найден в spec Публикации нет, пишется лог unknown channel key

  • key — имя канала, совпадающее с spec.key в UI и channel в прошивке.

      "name": "Датчик температуры",
      "type": "sensor",

      "status": "online",

Возвращает правила юнита (без фильтра — все). Правила с enabled: false возвращаются, но движок их не исполняет.

  • POST /rules

Создать правило (upsert по id: повторный POST с тем же id перезапишет правило).

Частичное обновление; для включения/выключения достаточно передать { "enabled": true|false }.

Удалить правило.

⧫ RulesService

Правила хранятся в MongoDB (коллекция rules, поле unitId связывает с юнитом) и наполняются сервисом seed при старте (SeedService). Отсутствующие в БД правила из seed-файла добавляются по id при каждом старте; существующие правила не перезаписываются.

При записи в БД подставляются переменные окружения (${ENV_VAR}) и выражения (${expr:...}).

{
  "rules": [
    {
      "id": "unique_rule_id",
      "name": "Температурный порог",
      "unitId": "unit-id-1",
      "trigger": {
        "topic": "sensor/unit-id-1/dht22",
        "qos": 0
      },
      "when": {
        "jsonpath": "$.temperature > 30"
      },
      "then": [
        {
          "action": "log",
          "params": {
            "level": "warn",
            "message": "Температура превысила порог: {{temperature}}°C"
          }
        },
        {
          "action": "publish",
          "params": {
            "topic": "alerts/high_temperature",
            "payload": "{\"value\": {{temperature}}, \"timestamp\": \"{{timestamp}}\"}",
            "qos": 1,
            "retain": false
          }
        }
      ],
      "enabled": true
    }
  ]
}

Структура

Поле Описание
id Уникальный идентификатор правила
name Название правила (опционально)
unitId ID юнита, к которому относится правило
trigger.topic Топик MQTT (строка или массив, поддерживает + и #)
trigger.qos Уровень QoS (0, 1, 2), по умолчанию 0
when Условие срабатывания (может быть опущено)
then Массив действий (не пустой)
enabled Флаг включения: правила с enabled: false не загружаются движком

Типы условий (when)

Тип Параметр Пример
topicRegex RegExp для топика "^sensor/.+/status$"
jsonpath $.field оператор значение "$.temperature > 30"
payloadEquals Точное совпадение payload "OK"
and Массив условий (И) [{...}, {...}]
or Массив условий (ИЛИ) [{...}, {...}]
not Одно условие (НЕ) {...}
timeBetween Временной интервал по часу (см. ниже) { "start": 22, "end": 6 }

Операторы jsonpath: ==, !=, >, >=, <, <=.
timeBetween — срабатывает, если текущий час (с учётом MOSCOW_OFFSET_HOUR, по умолчанию 3) попадает в интервал [start, end). При start > end интервал считается «через полночь». Параметры: start (number), end (number), опционально field — путь к ISO-дате в payload (иначе используется время получения сообщения).

{ "when": { "timeBetween": { "start": 22, "end": 6 } } }

Типы действий (then)

log — логирование в консоль:

  • level: info, warn, error
  • message: строка с плейсхолдерами {{fieldName}}

publish — публикация в топик:

  • topic: топик назначения
  • payload: строка с плейсхолдерами {{fieldName}}
  • qos: QoS (0, 1, 2), по умолчанию 0
  • retain: флаг retain (true/false), по умолчанию false

timeout — отложенный запуск вложенных действий:

  • delay: задержка в миллисекундах
  • then: массив действий, выполняемых после задержки
{ "action": "timeout", "params": { "delay": 5000, "then": [ { "action": "publish", "params": { "topic": "alerts/slow", "payload": "1" } } ] } }

Плейсхолдеры {{fieldName}} в payload/message заменяются значениями из JSON-контекста сообщения (доступ через jsonpath-путь $.fieldName).

Источники правил

Движок получает правила через провайдер, источник задаётся переменной RULES_SOURCE:

Источник Провайдер Поведение
mongo (по умолчанию) MongoRulesProvider Поллинг коллекции rules каждые 5 с (RULES_POLL_INTERVAL_MS), фильтр enabled !== false
api ApiRulesProvider Поллинг GET RULES_API_URL каждые 5 с, ожидает { "rules": [...] }, фильтр enabled !== false
file ConfigWatcher Следит за файлом CONFIG_PATH (по умолчанию ./rules.json), перечитывает при изменении

Во всех режимах набор правил пересобирается только при изменении сигнатуры (полного JSON) — при неизменных данных провайдер не вызывает перезагрузку. Изменение enabled в БД/API автоматически применяется движком на следующем поллинге (правило исключается из обработки).

Запуск (файловый режим)

MQTT_BROKER_URL=mqtt://localhost:1883 CONFIG_PATH=./rules.json npm start

Для MongoDB-режима: RULES_SOURCE=mongo MONGODB_URL=mongodb://... npm start.

⧫ Логи кластера

Логирование и диагностика кластера: единый JSON-конверт для всех компонентов, лог-топики и хранение в InfluxDB.

Формат

Все компоненты (device, server, rule-engine) публикуют логи в едином JSON-конверте в свои лог-топики. Telegraf отводит их в отдельный measurement logs в InfluxDB (бакет logs, retention 7 дней).

Лог-топики
Топик Источник
device/{unitId}/{objectId}/log ESP32 (device-log): старт/ребут, connect/disconnect, диагностика, хвост лога
server/worker/log Backend (Express): connect/disconnect/ошибки MQTT
rule-engine/worker/log MQTT Rule Engine: срабатывание/ошибки правил, connect/disconnect
Схема конверта
{
  "level":    "info",      // debug | info | warn | error
  "src":      "device",    // device | server | rule-engine
  "event":    "startup",   // startup|reboot|connect|disconnect|diag|rule-fired|rule-error|...
  "msg":      "человекочитаемый текст",
  "topic":    "device/unitId2/saspik.sa.wm.m001/log",
  "unitId":   "unitId2",   // device
  "objectId": "saspik.sa.wm.m001", // device
  "uptime":   12345,       // device, сек
  "cause":    "wifi-lost"  // device, при ребуте (wifi-lost | mqtt-timeout)
}
  • device: при старте публикует event=startup с хвостом лога в msg и причиной ребута в cause; при обрыве — event=diag с msg-сводкой и полями wifi/mqtt/lostSec; event=reboot перед перезапуском.
  • rule-engine: при срабатывании правила — event=rule-fired, при ошибке — event=rule-error.
  • server: при connect/disconnect/ошибке брокера — event=connect|disconnect|mqtt-error.

Хранение в InfluxDB

  • Measurement: logs (через name_override="logs" в telegraf).
  • Теги: topic, level, event, src, unitId, objectId.
  • Поля: msg, cause, uptime и др.
  • Бакет: logs (INFLUXDB_LOGS_BUCKET), retention 7 дней (INFLUXDB_LOGS_RETENTION_DAYS).
  • Сенсорные данные остаются в measurement mqtt_consumer (бакет mqtt).

Пример Flux-запроса по логам уровня error:

from(bucket: "logs")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "logs")
  |> filter(fn: (r) => r.level == "error")
  |> filter(fn: (r) => r._field == "msg")
  |> last()

Против спама

  • Mosquitto: log_type notice (без поштучного debug).
  • Rule Engine: не логирует каждое входящее сообщение — только срабатывания и ошибки правил.
  • Device: пишет только события (старт/ребут/connect/диагностика/обрыв), а не каждое чтение сенсора.

⧫ MQTT-топики

Централизованное описание топиков и форматов сообщений для обмена с MQTT-брокером кластера.

Все топики формируются по строгой структуре сегментов: {домен}/{unitId}/{objectId}[/суффикс]. Тип сегмента определяется положением, значения не меняют структуру.

Формат топика

Общий вид:

{домен}/{unitId}/{objectId}[/суффикс]
Домены
Домен Направление Пример
sensor/ device → broker (данные) sensor/unitId3/saspik-awqm001
device/.../command broker → device (команды) device/unitId3/saspik-awqm001/command
device/.../state device → broker (retained) device/unitId3/saspik-awqm001/state
device/.../status device → broker (retained) device/unitId3/saspik-awqm001/status
device/.../log device → broker (логи) device/unitId3/saspik-awqm001/log
units/{unitId}/commands/ команды реле units/unitId1/commands/a_relay1
units/{unitId}/sensors агрегированные данные units/unitId1/sensors
server/ логи backend (Express) server/worker/log
rule-engine/ логи MQTT Rule Engine rule-engine/worker/log
healthcheck/ healthcheck mosquitto healthcheck/ping
Сегменты
Сегмент Описание
{unitId} Идентификатор юнита (например unitId1, unitId2)
{objectId} Идентификатор объекта — сенсора или устройства (например saspik.sa.wm.m001)
{суффикс} Квалификатор топика: команда (commands/...), логи (/log)

Объект отвечает только за свои топики: к данным применяется sensor/, к управлению — device/, к диагностике — суффикс /log.

Нейминг объектов (постфиксы)

Идентификатор объекта в UI и БД состоит из базового идентификатора устройства и постфикса функциональной роли:

Постфикс Роль (тип объекта) Пример id
-sensor мониторинг (sensor) saspik.sa.wm.m003-sensor
-device автоматика (device) saspik.sa.wm.m003-device

Правила:

  • сегмент {objectId} в топике — всегда база без постфикса: для объекта saspik.sa.wm.m003-sensor топик будет sensor/unitId3/saspik.sa.wm.m003;
  • в прошивке OBJECT_ID задаётся базой без постфикса — публикация данных sensor/{unitId}/{base} и подписка на команды device/{unitId}/{base} совпадают с топиком объекта из UI;
  • сервер при создании объекта сам дописывает постфикс по типу и строит топик от базы, поэтому поле ID в форме содержит итоговое значение, которое уйдёт в базу;
  • объекты, созданные до постфиксов (например saspik.sa.wm.m003), совместимы: постфикс просто отсутствует, топики выводятся от того же базового идентификатора;
  • новые устройства автоматики: saspik-awqm001 (unitId3, local-mqtt) и saspik-aenm001 (unitId2, boilerplate); UI создаёт объект с постфиксом -device, в прошивке OBJECT_ID — база без постфикса.

Топики публикации (device → broker)

Показания сенсоров публикуются в sensor/{unitId}/{objectId}. Объекты-сенсоры делятся по модели датчика; канал объекта отображается на поле payload (см. ObjectsService, spec.key).

sensor/{unitId}/{objectId}

Payload — JSON-карта с произвольными именами каналов. Имена задаются
пользователем в config.h прошивки и в UI (spec.key); автоматического
discovery нет.

{
  "температура": 24.5,
  "влажность": 65.0,
  "свет": 1
}

Модель канала (DHT22, геркон и т.д.) определяет, какие ключи он публикует.
Двоичные сенсоры передаются как 0/1.

Топик формируется устройством из типа, юнита и id объекта:

String topic = String(OBJECT_TYPE) + '/' + String(UNIT_ID) + '/' + String(OBJECT_ID);

Топики команд (broker → device)

device/{unitId}/{objectId}/command

Команды на объект-устройство. Один топик на объект; имя канала передаётся в
payload, поэтому на одном объекте может быть сколько угодно автоматов.

{"channel": "свет", "value": "ON"}
{"channel": "полив", "value": "OFF"}
Структура
Поле Тип Описание
channel string Имя канала (spec.key в UI)
value string ON — включить, OFF — выключить

value также принимает 1/0 и TRUE/FALSE. Команда с неизвестным
channel игнорируется устройством. Legacy {"state":"ON"} без channel
поддерживается для старых объектов и применяется к первому автомату.

Старые объекты saspik.sa.* (например m003) сервер по-прежнему отправляет в
базовый топик device/{unitId}/{objectId} с payload {"state":"ON"|"OFF"} —
их прошивка не знает /command. Новые объекты (saspik-awqm001,
saspik-aenm001) используют /command.

Состояние и статус устройства

device/{unitId}/{objectId}/state

Retained-состояние всех автоматов объекта. Публикуется устройством при
подключении и после каждой смены; telegraf подписан на device/+/+/state и
складывает все строковые поля в Influx, откуда их читает UI.

{"свет": "ON", "полив": "OFF"}

Имена ключей совпадают с channel в командах и spec.key в UI.

device/{unitId}/{objectId}/status

Retained-статус присутствия. online публикуется при подключении, offline — LWT-сообщение брокера при обрыве соединения.

{"status": "online"}
{"status": "offline"}

Оба топика входят в ACL-правило device/# вместе с командами и логом.

⧫ Камера выращивания — гидропонная установка на 2 куста

Гидропонная установка для клубники (ebb & flow) на базе трубы ПВХ ø200 мм

Питательный раствор подаётся сверху помпой, заполняет трубу до уровня перелива,
затем самотеком сливается обратно в бак.
Управление помпой — через ESP32 + MQTT + rule-engine (SASPIK Cluster).

Описание

Параметры:

  • Количество кустов: 2
  • Субстрат: перлит
  • Длина трубы: 500–600 мм
  • Уровень заполнения: ~50 мм
  • Расположение бака: снизу под трубой, горизонтально, из той же трубы ø200 мм
  • Объём бака: ~15.7 л (500 мм длины)

Сенсорная камера — герметичный пластиковый корпус (ø75 мм × 100 мм) с вертикальным стояком-переливом внутри. При каждом сливе раствора из основной трубы камера заполняется, старая порция вытесняется через стояк в бак. После завершения слива в камере остаётся ~40 мм раствора, закрывающего датчики. При следующем цикле затопления новая порция промывает камеру и заменяет раствор.

Сборка

  1. Торцы: приклеить заглушки к обоим торцам трубы клеем для ПВХ.

  2. Слив: в дне трубы (в нижней точке уклона) вырезать отверстие под муфту ø50 мм. Вклеить муфту с переходом на шланг слива в бак.

  3. Отверстия под стаканы: разметить по центру верхней части трубы с шагом ~250 мм. Вырезать отверстия ø50–60 мм (по размеру стаканов).

  4. Перелив: в торцевой заглушке (противоположной сливу) или в верхней стенке установить вертикальный стояк высотой ~50 мм от дна трубы. Через него будет уходить избыток раствора.

  5. Подача: закрепить штуцер для трубки 8 мм сверху трубы. Трубка от помпы идёт вверх, вводится в трубу через штуцер.

  6. Уклон: установить трубу с уклоном ~2° в сторону слива (≈ 10 мм перепад на 500 мм длины).

  7. Помпа: поместить помпу в бак, подключить трубку подачи. Бак поставить под сливным отверстием.

  8. Стаканы: заполнить стаканы перлитом, установить в отверстия. Стаканы должны входить плотно, но до дна трубы не доставать (≈ 10–20 мм зазора).

  9. Бак:

    • Взять отрезок трубы ø200 мм × 500 мм.
    • Приклеить заглушки к обоим торцам.
    • Врезать штуцер 8 мм в нижней части одной из стенок — для забора раствора помпой.
    • В верхней части противоположной стенки врезать штуцер/фитинг для слива из сенсорной камеры.
    • В верхней части сделать отверстие под воздушный клапан (или просто небольшое отверстие ø3 мм для выравнивания давления).
    • Установить бак горизонтально под сливом из сенсорной камеры. Помпу разместить внутри бака или снаружи на заборном штуцере.

  10. Сенсорная камера:

  • Приклеить заглушку к нижнему торцу трубы ø75 мм (дно камеры).
  • Установить вертикальный стояк ø8 мм в дне камеры (высота 40 мм). Стояк — трубка, выходящая через дно наружу и отводящая избыток раствора в бак. Герметизировать место прохода.
  • Врезать входной фитинг в верхней части стенки камеры (от слива из основной трубы).
  • Закрепить датчики pH и EC через герметичные вводы в боковой стенке или сверху. Чувствительные элементы должны располагаться на высоте ~20 мм от дна (чтобы всегда были в растворе после слива).
  • Соединить слив из основной трубы с входом сенсорной камеры трубкой ø8 мм. Выход стояка направить в бак.

Подключение к SASPIK

  • ESP32 управляет реле помпы по MQTT-командам
  • MQTT-топик: greenhouse/grow_chamber/command
  • Формат команды:
{"state":"ON"}
{"state":"OFF"}
  • Цикл затопления настраивается через rule-engine в saspik-cluster (например: помпа ON на 10 мин, OFF на 50 мин)
  • Датчик уровня в трубе или таймер определяет длительность цикла

⧫ Архитектура esp32-boilerplate

SOLID-основа прошивок ESP32: три шаблона ролей (Gateway, Sensor, Device) на общей библиотеке saspik-core

Платформа — ESP32 / S2 / S3 / C3, framework — Arduino, сборка — PlatformIO.
Шаблон выбирается build-флагом -DDEVICE_ROLE (1 = Gateway, 2 = Sensor, 3 = Device).
Переиспользуемая логика — библиотека lib/saspik-core; приложения-шаблоны (src/app/) — композиционные корни (Composition Root).
Сборка, прошивка и конфигурация — в README скетча.
Контракт сообщений — единый JSON-конверт лога {level,src,event,msg,topic,unitId,objectId,uptime[,cause]} (см. mqtt-topics).

Общие решения

  1. DI через конструкторы/фабрики. Модули зависят от интерфейсов (IMqttClient, IEspNowClient, IConfigStore, ILogSink…), реализации подставляются в App — это же даёт моки для host-тестов.
  2. Два документированных исключения из «без глобалов». Переиспользуемые синглтоны WifiConfig и DeviceLog (shared-библиотеки, менять нельзя) изолированы за фасадами CaptivePortal и IRebootCauseStore; static s_instance внутри MqttManager/EspNowManager нужен для C-колбэков.
  3. Два источника конфигурации.
    • Compile-time: include/config.h — пины, интервалы, unitId/objectId, словари полей, таймауты.
    • Runtime: NVS. WiFi/MQTT — через captive portal (namespace saspik); параметры приложения — через ConfigManager (namespace saspik_app), по умолчанию из config.h. Правило merge: defaults ← NVS (побеждает NVS).
  4. Формат на проводе. MQTT — JSON (топики по mqtt-topics). ESP-NOW — бинарный пакет v2 (см. README); JSON в эфире не гоняем (лимит 250 байт). Мост ESP-NOW↔MQTT делает перевод binary→JSON.
  5. Неблокирующий loop. yield() в начале loop; MQTT connect не чаще MQTT_RECONNECT_INTERVAL_MS + socket timeout (защита от Task WDT, rst:0x8); авто-ребут по таймаутам WiFi/MQTT — только для Gateway/Device. Периодика — через TimerRegistry (overflow-safe разница millis()).
  6. Состав шаблонов.
    • Gateway: CaptivePortal, ConfigManager, WifiManager, MqttManager, Logger (UART+MQTT), EspNowManager, EspNowMqttBridge, TimerRegistry; опционально (Gateway-как-Device) — свои ISensor/IActuator.
    • Sensor: CaptivePortal (только при первом запуске), Logger (UART + ESP-NOW-лог через шлюз), EspNowManager (tx), InterfaceManager + ISensor, LightSleepManager, TimerRegistry. MQTT/WiFi STA после настройки не используются.
    • Device: CaptivePortal, ConfigManager, Logger (UART + ESP-NOW), EspNowManager (rx/tx), InterfaceManager + ISensor/IActuator, TimerRegistry.

Модули

CaptivePortal. Без изменений кода shared-библиотеки: begin() блокирует до 20 с на STA либо поднимает AP (DNS+HTTP), /save пишет в NVS и делает ESP.restart(). «Нет NVS → сразу портал» покрывает первый запуск.

ConfigManager. Merge-правило: defaults (config.h) ← NVS (saspik_app) ← DeviceConfig из портала (saspik, последний побеждает). config.h — единственное место «заводских» значений.

Logger. Собирает конверт и раздаёт по sink'ам. Startup-конверт с причиной ребута — после первого успешного MQTT-подключения. UART — всегда; MQTT/ESP-NOW — когда транспорт жив, иначе очередь drop-oldest.

MqttManager. Неблокирующий connect (интервал + socket timeout — против rst:0x8), retained online + LWT offline в /status, resubscribe после reconnect, авто-ребут по MQTT_REBOOT_TIMEOUT_MS, колбэк PubSubClient через статический указатель на this.

EspNowManager + EspNowCodec. Кодек: [type(1)][timestamp LE(4)][fieldId(1)+len(1)+data]*[crc8(1)], CRC-8/MAXIM; типы DATA/LOG/COMMAND/ACK; служебные поля 0xFF/0xFE — JSON лога/команды. Несовместим с v1 (node-sensor-1) — миграция узлов отдельная задача. Менеджер принимает пакеты в однослотовый RX-буфер и отдаёт их в update(), не в колбэке.

EspNowMqttBridge. Единственное место перевода binary↔JSON: узел→MQTT (data→JSON по fieldDict, log→конверт), MQTT→узел (команда→ESP-NOW как JSON без разбора). Маппинг objectId→MAC и словарь полей — статическая таблица в config.h.

InterfaceManager + шины. Фабрика создаёт по конфигу только нужные шины (пины — compile-time) и отдаёт их датчикам через конструкторы — инверсия контроля упрощает моки и переиспользование.

LightSleepManager. Таймерное пробуждение (esp_sleep_enable_timer_wakeup), накопленное время в RTC-памяти, отложенный вход в сон после flush лога, запрет сна при активном портале.

TimerRegistry. Задачи: чтение сенсоров, отправка данных, проверка сна. yield() вызывается в loop всегда, вне registry.

Открытые вопросы

  1. Light sleep + ESP-NOW (критично для Sensor). Штатный light sleep гасит радио — команды не доходят. Варианты: one-way TX (надёжно, но нет приёма), radio-on light sleep (приём возможен, но жрёт энергию — нужен стенд и замеры), store-and-forward на шлюзе. Стратегия канала ESP-NOW при роуминге STA — подтвердить.
  2. Runtime-конфиг вне портала. Портальная форма — только WiFi/MQTT. Интервалы, peer MAC, словари полей — defaults в config.h + переопределение через MQTT-команды в v2; без изменения shared WifiConfig.
  3. Адресация команд узлам. Проверить ACL брокера для device/{unitId}/+; объём и формат маппинга nodeObjectId→MAC и fieldDict на шлюзе (config.h v1 / NVS v2).

⧫ Индикация состояния связи

Светодиод как единственный канал диагностики, когда MQTT недоступен

Индикация живёт в GatewayApp поверх saspik-core и не требует ни брокера, ни сети, ни консоли.
Пока MQTT не поднят или открыт captive portal — светодиод мигает; после подключения пин возвращается каналу.
Настройка — константы STATUS_LED_* в include/config.h прошивки.

Зачем это нужно

Логи устройства уходят только в MQTT (device/{unitId}/{objectId}/log), поэтому при отсутствии связи плата не оставляет ни одного внешнего следа: данных нет, логов нет, статус в UI остаётся offline от последнего retained-сообщения. Снаружи живое устройство неотличимо от мёртвого, и диагностика сводится к физическому доступу и serial-консоли.

Индикация закрывает этот пробел: мигающий светодиод виден без терминала и сразу говорит «плата жива, но связи нет».

Что означает индикация

Состояние Светодиод Что это значит Что делать
открыт captive portal мигает, 2 Гц нет конфига в NVS, Wi-Fi не поднялся за 20 с или зажата кнопка портала; MQTT не запускается вовсе подключиться к SASPIK-XXXXXX, http://192.168.4.1/, задать SSID/пароль/host брокера
Wi-Fi есть, MQTT нет мигает, 2 Гц брокер недоступен: неверный host/порт/учётка, брокер лежит, ACL проверить адрес в портале, логи mosquitto, доступность порта 1883
всё подключено не мигает норма: пин отдан каналу led и показывает его состояние —
плата не стартует не горит вообще нет питания, bootloop, не прошита питание, serial-консоль 115200

Оба «плохих» состояния дают одинаковое мигание — различить их можно по эфиру: если рядом видна открытая сеть SASPIK-XXXXXX, плата в портале. Раздельные сигналы (например, разное число миганий) намеренно не вводились: см. «Ограничения».

Настройка

// include/config.h прошивки
constexpr int8_t   STATUS_LED_PIN = static_cast<int8_t>(PIN_GPIO_1);  // -1 = индикация выключена
constexpr bool     STATUS_LED_ACTIVE_LOW = true;  // LOW = светодиод горит
constexpr uint32_t STATUS_LED_BLINK_MS = 250UL;   // полупериод: 250 мс → 2 Гц
Параметр Смысл
STATUS_LED_PIN GPIO индикатора; -1 полностью выключает индикацию и оставляет пин каналу
STATUS_LED_ACTIVE_LOW полярность: true — активный низкий уровень (LOW = горит)
STATUS_LED_BLINK_MS полупериод мигания; полный цикл = 2 × значение

pinMode выставляется самим приложением при первом мигании, отдельной инициализации в скетче не требуется.

Сосуществование с каналом led

Индикация занимает тот же GPIO, что канал из CHANNELS[] (на DevKit V1 это встроенный светодиод GPIO 2):

  • пока связи нет, команды физически не могут прийти, поэтому мигание не конфликтует с управлением;
  • после подключения GatewayApp вызывает ChannelBank::refreshActuators() — пин возвращается каналу с прежним логическим состоянием, state не меняется;
  • STATUS_LED_ACTIVE_LOW должен совпадать с activeLow канала, иначе поведение будет инверсным.

Если индикатор нужен на отдельном пине, достаточно указать его в STATUS_LED_PIN — канал led останется на своём GPIO.

Связь с таймаутом портала

Портал не вечный: если за WIFI_CONFIG_PORTAL_TIMEOUT_MS (10 мин) к точке доступа никто не подключился и страницу не открывали, плата перезагружается и повторяет попытку STA. Поэтому мигание в портале может прекратиться само — это не сбой, а штатный выход из режима настройки, когда сеть наконец появилась.

Как проверить

Проверка Ожидание
включить плату без доступной сети через ~22 с (2 с опрос кнопки + 20 с Wi-Fi) появляется SASPIK-XXXXXX, светодиод мигает
настроить портал и сохранить плата перезагружается, мигание прекращается после connect
остановить брокер на 1–2 минуты мигание возобновляется, после подъёма брокера — прекращается
выставить STATUS_LED_PIN = -1 и прошить мигания нет, канал led работает как раньше

Косвенное подтверждение в логах брокера: New client connected … as gw-<objectId> — мигание прекращается синхронно с этим событием.

Распространение на другие прошивки

Индикация реализована в шаблоне GatewayApp, поэтому доступна любой прошивке на saspik-core с этим шаблоном. В esp32-boilerplate она по умолчанию выключена (STATUS_LED_PIN = -1), чтобы не занимать пины примеров; включается одной константой в config.h конкретного скетча.

Ограничения

  • Нет кодов «N миганий = ошибка X» — сигнал бинарный: мигает / не мигает. Расшифровка причины требует эфира (портал) или логов брокера.
  • Индикация не работает, если плата не дошла до loop() (bootloop, битая прошивка, просадка питания) — в этом случае светодиод просто не горит.
  • При STATUS_LED_PIN = -1 внешних признаков жизни, кроме появления точки доступа SASPIK-XXXXXX в режиме портала, у устройства нет.

См. также: MQTT-топики кластера — формат status и state, Классификация IoT-устройств — шифры objectId.

SOLID-база для прошивок ESP32 (Arduino framework, PlatformIO) с тремя шаблонами:
Gateway (шлюз), Sensor (сенсор), Device (устройство). Переиспользуемая

Протокол ESP-NOW (v2)

[type(1)] [timestamp LE(4)] [fieldId(1)+len(1)+data]* [crc8(1)]
  • Типы: 1=DATA, 2=LOG, 3=COMMAND, 4=ACK, 5=STATE.
  • Служебные поля: 0xFF — JSON лога, 0xFE — JSON команды,
    0xFD — JSON данных, 0xFC — JSON состояния.
  • Данные и состояние передаются JSON-картой с произвольными именами каналов:
    {"свет":1} и {"свет":"ON","полив":"OFF"}; legacy float-поля
    (FIELD_DICTIONARY) поддерживаются для совместимости.
  • CRC-8/MAXIM (полином 0x31 отражённый → 0x8C, init 0x00).
  • Лимит пакета — 250 байт (ESP_NOW_PACKET_MAX).
  • Несовместим с v1 (node-sensor-1); миграция узлов — отдельная задача.

Каналы и команды

constexpr ChannelConfig CHANNELS[] = {
    {"свет", nullptr, 13, ChannelRole::Actuator, ChannelModel::Relay, false, false},
    {"полив", nullptr, 26, ChannelRole::Actuator, ChannelModel::Relay, false, false},
};
  • key — имя канала; должно совпадать с spec.key объекта в UI.
  • key2 — второй ключ DHT22 (например, влажность), иначе nullptr.
  • role — Sensor или Actuator; model — Dht22, Float, Relay, Led.
  • activeLow — для LED/реле; mock — для сенсоров без железа.

⧫ device-log

Энергонезависимое хранение причины ребута для ESP32 (Arduino / PlatformIO) в NVS

Диагностические события публикуются в MQTT в едином JSON-конверте; здесь
фиксируется только причина последнего перезапуска, которая переживает
перезагрузку и потерю питания.

История: ранее библиотека вела кольцевой файловый лог на LittleFS. Запись в LittleFS во время активного WiFi вызывала зависания/ресеты (flash-latency и нестабильность питания). По решению от файлового лога отказались — осталась только запись reboot-cause в NVS + публикация событий в MQTT.

Возможности

  • NVS-причина ребута: setRebootCause()/rebootCause() — причина последнего ребута, не сбрасывается после чтения
  • Редкая, малая запись в NVS — минимум flash-операций, стабильность при активном WiFi
  • Без внешних зависимостей: Preferences из ESP32 Arduino Core

Подключение к проекту

В platformio.ini добавьте путь к общему каталогу библиотек:

lib_extra_dirs =
    ../shared

Использование

#include "DeviceLog.h"

void setup() {
    DeviceLog.begin();

    // Причина предыдущего ребута (из NVS)
    if (DeviceLog.hasRebootCause()) {
        Serial.println(DeviceLog.rebootCause());
    }
}

void loop() {
    // произошёл сбой — фиксируем причину и перезагружаемся
    DeviceLog.setRebootCause("mqtt-timeout");
    ESP.restart();
}

⧫ Saspik-meshrover

MeshRover — рой автономных ботов для точной прополки полей без GPS

ESP32-S3: UWB (DWM3000), IMU, энкодеры, OV2640, TFLite Micro.
LoRa mesh (433/868 МГц) + Raspberry Pi базовая станция.
Фаза: Pre-MVP, этап 1 — UWB-дальномер на двух ESP32.

Цель

Создать рой из лёгких автономных ботов, способных без GPS и постоянного интернета совместно обрабатывать поле, передавая на базовую станцию только метаданные детекций.

Ключевые технологии

ESP32-S3, UWB (DWM3000), LoRa mesh, TensorFlow Lite Micro, Raspberry Pi, распределённая локализация.

Текущий статус

Pre-MVP. Начат этап 1: UWB-дальномер на двух ESP32.

План работ

Этап 1: UWB-дальномер (текущий)

  • Настроить PlatformIO проект для ESP32-S3 + DWM3000
  • Инициализировать DWM3000 на двух платах
  • Реализовать TWR (Two-Way Ranging) на одной паре
  • Вывести дальность в UART / Serial Plotter
  • Измерить точность на дистанциях 1–50 м

Этап 2: Локальная навигация

  • Подключить IMU (MPU6050/ICM-20948)
  • Реализовать счисление пути (dead reckoning)
  • Связать UWB + IMU + энкодеры в EKF
  • Получить стабильные координаты относительно опорной точки

Этап 3: LoRa-сеть

  • Настроить LoRa-модуль (SX1276/SX1262)
  • Реализовать простой flooding mesh
  • Пакет: координаты + статус (50–150 байт)
  • Тест: 3+ узла в mesh

Этап 4: Базовое зрение

  • Подключить камеру OV2640 к ESP32-S3
  • Собрать датасет (культура/сорняк)
  • Обучить TFLite-модель (2 класса)
  • Запустить инференс на ESP32-S3

Этап 5: Оркестрация

  • Базовый веб-интерфейс на RPi
  • Приём LoRa-пакетов на RPi
  • Построение карты покрытия
  • Алгоритм виртуальных сил для перераспределения секторов

Бэклог

  • CLI для отладки UWB
  • Симулятор роя (для тестов без железа)
  • Документация по протоколу пакетов

Утверждённая архитектура (конспект)

Каждый бот (ESP32-S3)

  • Собирает UWB-дальности до соседей, опрашивает IMU и энкодеры.
  • Ведёт счисление пути и вычисляет свои координаты (EKF) относительно опорных точек роя.
  • Имеет камеру OV2640 и выполняет на борту инференс простой TFLite-модели (2 класса: культура/сорняк).
  • Каждое обнаружение упаковывает в короткий пакет (свои координаты, координаты цели, класс, уверенность) и отправляет в общий LoRa-mesh.
  • Получает от базы или соседей задания на коррекцию маршрута, но может работать автономно при обрыве связи.
  • Реагирует на соседей: избегает столкновений, перераспределяет сектора покрытия по алгоритму виртуальных сил.

Базовая станция (Raspberry Pi + LoRa-модуль)

  • Участвует в mesh как привилегированный узел.
  • Аккумулирует все пакеты с детекциями.
  • Строит единую оперативную карту прополки/посева.
  • Выявляет пропущенные участки, оптимизирует глобальное покрытие.
  • Отправляет ботам рекомендательные команды («проверить зону», «сместить фокус»).
  • Предоставляет веб-интерфейс оператору с картой, статусом, зарядом.
Локальная версия для первых тестов (Docker)

На этапах 1–3 базовая станция запускается локально в Docker на машине разработчика:

  • Принимает UART-логи с ESP32 через проброшенный USB (последовательный порт).
  • Логирует и отображает дальномерные данные, позже — координаты и LoRa-пакеты.
  • Веб-интерфейс (FastAPI + легковесный фронтенд) для визуализации в реальном времени.
  • Контейнерная сборка: одна команда docker compose up для поднятия всего стека.
  • Переход на RPi произойдёт на этапе полевых испытаний (Stage 4–5).

Сеть

  • UWB — для точной относительной навигации (без GPS).
  • LoRa (433/868 МГц, mesh) — для обмена координатами, статусом, метаданными детекций и командами.
  • Данные, передаваемые по LoRa, компактны (50–150 байт), что укладывается в возможности технологии.
  • Никакой сырой видеопоток по LoRa не идёт.

Дополнительно (опция, не для MVP)

Позже можно добавить Raspberry Pi на отдельных ботов-лидеров, если понадобится более сложное зрение прямо в поле. Но текущий стек позволяет начать без него.

Соединение ESP32-S3 ↔ DWM3000 (SPI)

ESP32-S3           DWM3000 (24-контактный модуль, 13 × 23 мм)
────────           ───────────────────────────
GPIO 10 (SPI CS)   →  CS
GPIO 11 (SPI MOSI) →  MOSI
GPIO 12 (SPI MISO) ←  MISO
GPIO 13 (SPI SCK)  →  SCK
GPIO 14            →  RSTn
GPIO 15            ←  IRQ
3.3V               →  VDD1 (5), VDD3V3 (6, 7)
GND                →  VSS (8, 16, 21, 23, 24)

Пин-аут сверен с software/include/pins.h (SPI2_HOST, GPIO10–15). DWM3000 работает в SPI Mode 0, тактовая частота до 23 МГц — текущие 20 МГц в config.h корректны.

Питание

LiPo 3.7V → LDO 3.3V → ESP32-S3 VDD33
                     → DWM3000 VDD1 (5) + VDD3V3 (6, 7) — 3,3 В на все три вывода

Внутренние 1,8 В DWM3000 делает сам; наружу они не выведены.

Цоколёвка DWM3000 сверена с Qorvo DWM3000 Data Sheet Rev B, Table 2:
VDD1 — контакт 5, VDD3V3 — контакты 6 и 7, VSS — 8, 16, 21, 23, 24, RSTn — 3,
SPICSn/SPIMOSI/SPIMISO/SPICLK — 17/18/19/20, GPIO8/IRQ — 22.
Прежняя запись «VDD — выход внутреннего регулятора 1,8 В» неверна: выводов 1,8 В у модуля нет.
Корпус — 13 × 23 мм, 24 контакта, площадки 1,6 × 1,0 мм с шагом 1,4 мм (там же, § 7.2).

  • Питание через USB от ноутбука.

Альтернативные пины для кастомной платы

Отдельного HSPI у ESP32-S3 нет: SPI2_HOST выводится на любые свободные GPIO через
матрицу выводов, поэтому «переезд» SPI — это правка pins.h и config.h, без переделки схемы.
Занятые сейчас GPIO10–15 менять без необходимости не нужно.

  • Прошивка lib/dwm3000 написана под DW3110 и почищена от DW1000-регистров; все устаревшие упоминания DW1000 схемно неактуальны.

Ориентация: посадки зеркальны

Плата начерчена зеркально по вертикали (по требованию заказчика): ряд J1 розетки — сверху,
DWM3000 с антенной — вверху справа, кипер-аут — в правом верхнем углу. Это значит, что модули
и элементы ставятся со стороны пайки, а медь смотрит вниз.

Если плата собирается обычным способом — медью вверх, — в генераторе ставится MIRROR_Y = False,
и вся геометрия (посадки, медь, шелкография, подписи) пересчитывается обратно без правок.

Что где на плате

  • J1 — клеммник 5 В; F1 — самовосстанавливающийся предохранитель 1,1 А.
  • U1 — AMS1117-3.3, питает только DWM3000 (0,16 А в пике, 0,27 Вт).
  • J2 — розетка 2×22 под DevKitC-1: контакт 1 слева, ряд J1 — верхний.
  • U2 — DWM3000; антенна смотрит вправо, зона x 53…73, y 0…17 мм — кипер-аут без меди.
  • J3 — гребёнка UART 1×3 (TX, RX, GND); LED1 — индикация 5 В; LED2 — статус на GPIO48.
  • Четыре проволочные перемычки (все в BOM, показаны пунктиром на листе 2): IRQ и RST —
    обходятся веер SPI и шина 3,3 В; две GND — соединяют землю модуля и конденсаторов
    с основным полигоном.
  • Кнопки BOOT/RESET и USB — на самом DevKit, на носителе не дублируются.

  2. Этой же мощностью — плату. Если зазоры выходят уже/шире нужного, правится не файл,
    а «kerf» в LightBurn (отрицательное смещение ≈ половина ширины пятна).
  3. Смыть/стереть остатки маски, стравить медь, просверлить по DRILLS, обрезать по CUT_EDGE.

Калибровка (по опыту, порядок важен):

  • Ширина пятна (kerf) — главное число: слой KERF в купоне, одна линия, замерить
    ширину под лупой. Line interval в заливке ставить ≈ kerf / 2.
  • Фокус — ramp-тест на обрезке: самая узкая линия и есть фокус. Если на чистую щель
    уходит 4–5 проходов, это почти всегда расфокус, а не нехватка мощности.
  • Обдув — воздух 0,5–1 бар, сопло 2–3 мм, поток вдоль реза. Без него продукты горения
    осаживаются обратно и проходов нужно в 2–3 раза больше.
  • Скорость и мощность — 5 проходов на 4000 мм/мин ≈ 1 проход на 800 мм/мин по энергии,
    но хуже по качеству (переосаждение, нагрев меди). Обычно лучше 1000–1500 мм/мин,
    70–100 %, 1–2 прохода.
  • Маска — два тонких матовых слоя вместо одного толстого; тёмная краска поглощает лучше.
  • Угол сканирования — у диодника пятно прямоугольное: 0° и 90° дают разную ширину щели,
    проверить оба.

Если после калибровки станок уверенно держит только 0,5 мм — плату надо переразвести под
этот зазор (в текущей разводке мест теснее 0,5 мм всего 8).

Компенсация пятна (kerf)

Вектор в DXF — это ось луча, а не край прожига: лазер снимает полосу шириной kerf
вокруг линии. Поэтому зона выжигания в файле ужимается на kerf/2 с каждой стороны,
и тогда:

снятая маска = геометрия + kerf = (зазор − kerf) + kerf = зазор

Без этой компенсации заливка выжигает маску и над дорожкой, и дорожка 0,3 мм после
травления остаётся 0,1–0,2.

Файл собран с --kerf=0.3 (станок с пятном 0,3 мм). Разводка подогнана под это:
минимальный зазор по меди — 0,4 мм, то есть после ужатия остаётся полоса 0,1 мм,
она прожигается слоем заливки с интервалом 0,07–0,08.

Если замер по слою KERF дал меньше (0,2–0,25) — файл можно пересобрать с меньшим kerf,
пропадёт лишняя компенсация:

python3 esp32s3-dwm3000-board.py --laser --kerf=0.25 --hatch-step=0.08

Правило: геометрия минус kerf = минимально воспроизводимый зазор. При пятне 0,3 зазор
0,3 в файле исчезает совсем (прожигать нечего), поэтому в разводке минимальный зазор
поднят до 0,4: остаётся полоса 0,1, которая гарантированно жжётся.

Что пришлось расширить под 0,3:

  • веер SPI — шаг между дорожками 0,7 мм (0,3 дорожка + 0,4 зазор);
  • RST опущен, чтобы отойти от шины 3,3 В;
  • площадки розетки J2 уменьшены с 1,6 до 1,5 мм (кольцо 0,25 мм при отверстии 1,0) —
    зазор между контактами стал 1,04 мм, проход RST по нему — 0,52 мм;
  • площадки DWM3000 уменьшены с 1,6 × 1,0 до 1,2 × 0,8 мм: у даташитного посадочного места
    угловые контакты 16 (GND) и 17 (SPICSn) стояли в 0,21 мм — при пятне 0,3 эта щель
    не выжигается и CS замыкается на землю. После уменьшения зазор 0,51 мм, по рядам 0,60 мм.

Режим: заливка, а не контур

Контуром (Line по замкнутой фигуре) жгутся только стенки. Щель 0,2 мм при этом
«закрашивается» — две стенки сливаются, потому что луч шире половины щели. Щель 0,3 мм
оставляет внутри непрожжённую полосу. Поэтому узкие зоны — только Fill, а контуром
имеет смысл обходить широкие области (кипер-аут антенны 10 × 17 мм), да и там при
интервале больше kerf останется гребень.

Проверенный режим (диодный лазер, снятие маски)

Подобрано на купоне, даёт чистую щель без поджога меди:

Параметр Значение
Мощность 40 % (100 % хуже: краска карбонизуется и мешает)
Скорость 1000 мм/мин
Проходов 3, между 2-м и 3-м стереть нагар тряпкой
Line interval 0,07–0,08 мм (≈ kerf / 2; при 0,15 в щели 0,3 остаётся непрожжённая полоса)
Ориентация Cross-hatch, если есть: второй проход поперёк

Почему интервал критичен: если шаг заливки больше ширины щели, лазер прожигает
её края, а в середине остаётся полоса маски — именно это даёт «0,3 и выше оставили
щель внутри», тогда как 0,2 закрашивается насквозь.

Зазоры меньше ~0,25 мм на таком пятне схлопываются (медь съедается), поэтому
проектная норма 0,3 мм — это нижняя рабочая граница, а не запас.

Время на плату (8,75 см² негатива, 3 прохода при 1000 мм/мин):

0,10 мм 5,1 м ~15 мин

Три варианта подачи файла (выбрать по своему станку):

  • вектор + заливка (рекомендую) — точные края, время по площади; нужен LightBurn или
    аналог с заливкой;

    для станков с режимом гравировки изображения (проверить DPI в станке).

выделить всё вместе с прямоугольником вокруг платы и вычесть медь из прямоугольника
